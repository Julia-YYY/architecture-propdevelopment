## 1. Контекст

**Пользователи:**

- Собственник или жилец работает через мобильное приложение. Он управляет доступом, отвечает на вызовы домофона, проходит в дом по лицу и въезжает по госномеру.
- Гость или курьер звонит в квартиру через домофон.
- Диспетчер УК или охрана просматривает журнал доступа по своему ЖК.

**Системы:**

- PropDevelopment (сервисы ЖКУ) — система в фокусе. Она является источником истины о собственниках, помещениях и правах доступа.
- Платформа «Умный дом» партнёра — внешняя система. Она управляет устройствами, распознаёт лица и номера, содержит медиасервер видеовызовов.
- Устройства партнёра: интеллектуальный домофон и интеллектуальный шлагбаум.
- Система УК — существующий партнёр.
- APNs/FCM — сервисы push-уведомлений.

## 2. Изменения в ландшафте (диаграмма контейнеров)

| Элемент | Тип | Назначение | Почему нужен |
| --- | --- | --- | --- |
| **smart-home-service** | Новый контейнер (Kotlin, Spring Boot) | Права доступа жильцов и гостей, госномера, согласия на биометрию, команды открытия, выдача одноразовых токенов видеовызова, журнал событий | Отделяет критичный домен физического доступа от tenant-core-app: свой цикл релизов, отдельный контур безопасности, отдельные права |
| **smart-home-db** | Новая БД (PostgreSQL, TDE и шифрование колонок) | Права, госномера, согласия, **ссылки** на биометрические ID партнёра, журнал событий с ограниченным сроком хранения | Замкнутый контур для секретных данных. **Не реплицируется в DWH по CDC** без обезличивания |
| **partner-integration-gateway** | Новый контейнер (API Gateway + адаптер, anti-corruption layer) | Единая точка входа и выхода для API партнёров. | **secrets-vault** | Новый контейнер (HashiCorp Vault) | Сертификаты mTLS, client secret, ключи HMAC, их ротация | Секреты не хранятся в коде и конфигурации |

| Платформа «Умный дом» партнёра | Новая внешняя система | Устройства, распознавание, медиасервер | |

| Мобильное приложение → smart-home-service | Новая связь | REST/HTTPS, JWT от auth-service-1 | Новые функции работают в существующем приложении |
| smart-home-service → CRM собственников | Новая связь | Проверка, что пользователь — собственник или жилец помещения | Источник истины о владении |
| Мобильное приложение → платформа партнёра | Новая связь | Видеопоток WebRTC/SRTP по одноразовому токену | Видео не проходит через инфраструктуру PropDevelopment и не хранится в ней |

## 3. Требования к безопасности

### 3.1. Биометрия и ПДн (152-ФЗ, 572-ФЗ)

| ID | Требование |
| --- | --- |
| SEC-01 | Биометрию включает только сам собственник или жилец (opt-in) после отдельного **письменного согласия** на обработку биометрических ПДн (ст. 11 152-ФЗ) в приложении с ЭП/OTP. Согласие можно отозвать в один клик, после чего шаблон удаляется у партнёра в течение 24 часов, а удаление подтверждается обратным вызовом |
| SEC-02 | PropDevelopment **не хранит** фото и биометрические шаблоны. Фото при регистрации передаётся партнёру транзитом через шлюз без сохранения на диске и в логах. В smart-home-db хранится только ссылка `face_ref_id` |
| SEC-03 | По договору с партнёром: он является обработчиком ПДн по поручению (ч. 3 ст. 6 152-ФЗ), хранит данные на территории РФ (ч. 5 ст. 18), имеет аттестованную ИСПДн нужного уровня защищённости, предоставляет отчёты об аудите и уведомляет об инцидентах не позднее чем через 24 часа |
| SEC-04 | Гостям биометрический доступ не выдаётся, только одноразовые или временные коды и приглашения со сроком действия |
| SEC-05 | Госномера и журналы событий хранятся ограниченный срок (предлагается 90 дней для событий, видео у партнёра — не более 30 дней) и затем автоматически уничтожаются |
| SEC-06 | В DWH передаются только обезличенные агрегаты (число проходов по ЖК и часам). Сырые события, госномера и `face_ref_id` в DWH не передаются |
| SEC-07 | В push-уведомлениях нет ПДн, только идентификатор события. Детали приложение запрашивает по защищённому каналу |

### 3.2. Изоляция и авторизация

| ID | Требование |
| --- | --- |
| SEC-10 | Каждый запрос к партнёру и от партнёра несёт `complex_id`, а шлюз проверяет его по токену (ABAC). Партнёр не может получить или изменить данные ЖК, к которому не привязан его client (защита от BOLA, OWASP API1) |
| SEC-11 | Право открыть дверь или шлагбаум выдаётся только при подтверждённой связи «пользователь — помещение — подъезд или парковка» из CRM собственников. Права отзываются автоматически при смене собственника или окончании аренды |
| SEC-12 | Команда «открыть» — одноразовая: в ней есть `nonce`, `timestamp` (окно ±30 с) и подпись. Повторное воспроизведение отклоняется |
| SEC-13 | Чувствительные операции (включение биометрии, добавление госномера, выдача постоянного доступа другому человеку) требуют повторной аутентификации: биометрия устройства или OTP (step-up) |
| SEC-14 | Сотрудники УК видят журнал только своего ЖК, без фото и госномеров в открытом виде (маскирование) |

### 3.3. Защита каналов и инфраструктуры

| ID | Требование |
| --- | --- |
| SEC-20 | Весь обмен с партнёром идёт по TLS 1.2+ (лучше 1.3) с **mTLS**. Сертификаты выпускает и ротирует secrets-vault, срок жизни не более 90 дней |
| SEC-21 | Партнёр обращается только к partner-integration-gateway в DMZ, по allowlist IP. Прямого сетевого доступа к smart-home-service и БД нет. В Kubernetes это закреплено NetworkPolicy (как в задании 5) |
| SEC-22 | Исходящий трафик к партнёру разрешён только со шлюза (egress-политика межсетевого экрана) |
| SEC-23 | Шлюз валидирует запросы и ответы по схеме OpenAPI и отбрасывает лишние поля, чтобы ПДн не утекали в ответах (OWASP API3) |
| SEC-24 | Rate limiting на партнёра и на пользователя, защита от перебора кодов гостей |
| SEC-25 | Приложение собственника использует certificate pinning, хранит токены в Keychain/Keystore и проверяет root/jailbreak |
| SEC-26 | Все команды открытия, изменения прав, обращения партнёра и отказы авторизации журналируются в SIEM. Настроены алерты: массовые отказы, доступ к чужому `complex_id`, открытие ночью без события распознавания |
| SEC-27 | Безопасный отказ: если интеграция недоступна, домофон работает в локальном режиме партнёра (физический ключ или код). Отказ PropDevelopment не должен блокировать выход людей из дома (требования пожарной безопасности) |
| SEC-28 | Перед запуском проводится моделирование угроз (STRIDE), пентест API и согласование со специалистом ИБ как обязательный шаг процесса изменений |

## 4. Протоколы аутентификации и авторизации

| Взаимодействие | Аутентификация | Авторизация |
| --- | --- | --- |
| Собственник → мобильное приложение → smart-home-service | **OpenID Connect**, Authorization Code + **PKCE** через существующий auth-service-1 (Keycloak). Access token JWT живёт 5 минут, refresh token ротируется | Scope `smart-home:read`, `smart-home:open`, `smart-home:manage`. Права на объект (подъезд, шлагбаум) smart-home-service проверяет по CRM (RBAC + ABAC по `owner_id` и `premise_id`) |
| Чувствительные операции | Step-up: claim `acr` с повышенным уровнем (OTP или биометрия устройства) | Политика в smart-home-service |
| smart-home-service ↔ partner-integration-gateway (внутри) | mTLS сервис-к-сервису (сертификаты из Vault или service mesh) | Allowlist сервисов на шлюзе |
| PropDevelopment → платформа партнёра | **mTLS** и **OAuth 2.0 Client Credentials**. Токен партнёра хранится в шлюзе, у клиентов его нет. Лучше использовать токены, привязанные к сертификату (RFC 8705) | Scope от партнёра, ограниченные ЖК PropDevelopment |
| Платформа партнёра → PropDevelopment (вебхуки) | **mTLS** и подпись тела **HMAC-SHA256** (заголовки `X-Signature`, `X-Timestamp`, `X-Nonce`) | Шлюз сверяет `complex_id` события со списком, разрешённым этому партнёру |
| Мобильное приложение → медиасервер партнёра (видео) | Одноразовый **короткоживущий токен** (JWT, 60 с, audience = медиасервер). Его выдаёт smart-home-service после проверки прав | Токен привязан к конкретному вызову и устройству |
| Сотрудник УК → журнал доступа | SSO (OIDC через Keycloak или федерация с AD), MFA | ABAC по `uk_id` и `complex_id` |

## 5. Организация взаимодействия с внешней платформой

**Принципы.** Вся интеграция с партнёром идёт через partner-integration-gateway, который работает как anti-corruption layer. Внутренняя модель PropDevelopment не зависит от API партнёра. Синхронные команды передаются по REST, события партнёра приходят вебхуками и обрабатываются идемпотентно.

### 5.1. Сценарии

1. **Регистрация лица.** Приложение → smart-home-service. Проверяются согласие и step-up. Шлюз передаёт фото партнёру (`POST /faces`). Партнёр возвращает `face_ref_id`, он сохраняется в smart-home-db. Фото нигде не сохраняется.
2. **Добавление госномера.** Приложение → smart-home-service. Проверяется право на парковку по CRM. Шлюз отправляет `PUT /barriers/{id}/whitelist`. Изменение пишется в аудит.
3. **Автоматический проход или въезд.** Устройство распознаёт лицо или номер, платформа партнёра сверяет его с белым списком и открывает. Вебхук `access.granted` или `access.denied` приходит в шлюз, затем в smart-home-service, который записывает журнал и шлёт push собственнику (если тот подписан).
4. **Вызов домофона.** Вебхук `call.incoming` приходит в шлюз, затем в smart-home-service, который отправляет push без ПДн. Приложение запрашивает токен видеовызова и подключается к медиасерверу по WebRTC. Нажатие «Открыть» → smart-home-service → шлюз → `POST /doors/{id}/open`, команда одноразовая и подписанная.
5. **Смена собственника.** CRM сообщает об изменении. smart-home-service отзывает права, удаляет госномера и запрашивает удаление `face_ref_id` у партнёра.
6. **Ночная сверка.** Шлюз раз в сутки сверяет белые списки партнёра с smart-home-db. Расхождения считаются инцидентом и уходят в SIEM.

### 5.2. Технические требования к интеграции

| ID | Требование |
| --- | --- |
| INT-01 | Контракты описаны в OpenAPI 3 (REST) и AsyncAPI (вебхуки), версионируются (`/v1`). Изменения проходят согласование с ИБ |
| INT-02 | Вебхуки идемпотентны (`event_id`) и доставляются по принципу at-least-once: партнёр повторяет с экспоненциальной задержкой. Шлюз отвечает 2xx только после записи события |
| INT-03 | Синхронные вызовы с таймаутом 2 с, circuit breaker и ограниченным числом повторов (только для идемпотентных операций) |
| INT-04 | Корреляционный ID (`X-Request-ID`) сквозной: приложение → сервис → шлюз → партнёр → аудит |
| INT-05 | SLA партнёра: доступность API не ниже 99,9 %, задержка открытия по команде не больше 2 с (p95), уведомление о плановых работах за 72 часа |
| INT-06 | Отдельные среды партнёра (sandbox, prod) с разными сертификатами. В sandbox нет реальных ПДн |
| INT-07 | Мониторинг: метрики шлюза (ошибки, задержки, отказы авторизации) и алерты на деградацию |
| INT-08 | Выход из партнёрства: в договоре закреплены выгрузка и удаление данных у партнёра. Благодаря anti-corruption layer партнёра можно сменить без изменения мобильного приложения |
